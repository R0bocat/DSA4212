# How much does general text help a small language model learn a narrow domain?

Small decoder-only language models (13.9M parameters) trained **from scratch** on PubMed abstracts mixed with
FineWeb-Edu, under a fixed budget of **300M training tokens** (about 41 minutes on one AMD RX 6900 XT, fp16).
We vary the domain share $\delta$, the amount of unique domain data $U$, regularisation, the training horizon, and
how PubMed-like the general data is.

- **Report:** [`report/`](report/) — LaTeX source, bibliography and figures.
- **Authors:** [`authors.md`](authors.md).

## Repository layout

Every script resolves its paths relative to the repository root, so all commands below work from any directory.

| path | contents |
|---|---|
| `code/` | experiment, data-preparation, analysis and plotting code |
| `runs/` | one folder per training run: `summary.json`, `log.jsonl`, `stdout.txt` (checkpoints `best.pt` are **not** committed, ~65 MB each) |
| `results/` | aggregated numbers: `results.csv` (one row per run), `pools_summary.json`, `pools_summary_d.json`, `run_plan.txt`, `data_stats/` |
| `report/` | the submitted report: `report.tex`, `references.bib`, `figures/` (generated by `code/analyze*.py`) |
| `tokenizers/` | `mix8192.json`, the shared byte-level BPE tokenizer used by every run |
| `RCOm-windows-gfx1030/` | GPU / PyTorch setup notes and the scripts that install the ROCm build |
| `data/` | **empty in the repo** (too large); filled by the data-preparation steps below. The one exception is `data/similarity/scores.npz` (~28 MB), which is committed because it cannot be regenerated without a GPU |

## Environment and dependencies

### Hardware and OS

- AMD Radeon RX 6900 XT (gfx1030, RDNA2, 16 GB), Windows 11.
- One run of 300M tokens takes about 41 minutes; every run was hard-capped at 45 minutes and none were truncated.

### PyTorch / ROCm

Official PyTorch ROCm Windows wheels do **not** detect this GPU. AMD's nightly gfx103X wheels do, via the community
project <https://github.com/ssubedir/RCOm-windows-gfx1030>, which is vendored in
[`RCOm-windows-gfx1030/`](RCOm-windows-gfx1030/). See its `README.md` for the full install and troubleshooting guide.

Versions used by every reported run (recorded in each `runs/*/summary.json`):

| component | version |
|---|---|
| PyTorch | `2.10.0+rocm7.12.0a20260204` |
| HIP | `7.2.0` |
| Python | `3.12.16` |
| AMD driver | 26.10.1 |

Setup:

```
git clone https://github.com/ssubedir/RCOm-windows-gfx1030
cd RCOm-windows-gfx1030
.\scripts\setup-nightly.bat
.\activate.bat
```

Verify the GPU is visible before training:

```
python code/check_gpu.py
```

Nightly wheels can disappear from the index. If they do, any PyTorch build that sees the GPU will work, but timings
and the last digits of the results will differ.

### Python packages

```
pip install -r requirements.txt
```

`requirements.txt` pins the versions used: `numpy`, `tokenizers`, `pyarrow`, `datasets`, `huggingface_hub`,
`matplotlib`. PyTorch is installed by the ROCm setup above, not by `requirements.txt`.

### Precision

**fp16 is used everywhere.** On this GPU bf16 is 7–11× slower than fp32, while fp16 is the fastest option
(about 131k tokens/s for the 13.9M model). `code/bench_tokens_per_sec.py --dtype {fp16,fp32,bf16}` reproduces the
comparison.

## Data preparation

About 1–2 h of CPU time plus downloads; needs roughly 25 GB of free disk.

### 1. PubMed abstracts (domain)

Six train shards from the Pile mirror, ~2.3 GB of text:

```
python code/inspect_corpus.py --repo ArmelR/the-pile-splitted --prefix "data/PubMed Abstracts/train/" --download "data/PubMed Abstracts/train/data-0000[0-5]-of-*.arrow" --out data/pubmed_raw
python code/prepare_data.py --src data/pubmed_raw --out data/pubmed_v2 --filters minimal --max-para-chars 100000 --min-doc-chars 300 --val-frac 0.002 --test-frac 0.002 --clean-only
```

### 2. FineWeb-Edu (general)

`sample-10BT` shard 0. Shard 1 is only needed for the similarity pools (see the similarity extension below).

```
python code/inspect_corpus.py --repo HuggingFaceFW/fineweb-edu --prefix "sample/10BT/" --download "sample/10BT/000_00000.parquet" --out data/fineweb_raw
python code/prepare_data.py --src data/fineweb_raw --out data/fineweb_v1 --filters minimal --max-para-chars 100000 --min-doc-chars 300 --val-frac 0.002 --test-frac 0.002 --max-train-mb 1600 --clean-only
```

### 3. Decontaminate, fit the shared tokenizer, encode

Remove PubMed val/test abstracts that also occur in the FineWeb training text, then fit one tokenizer on an
equal-bytes mix of both corpora and encode every split with it:

```
python code/overlap_check.py --reference data/fineweb_v1/clean_train.jsonl --targets data/pubmed_v2/clean_val.jsonl data/pubmed_v2/clean_test.jsonl --flagged-out flagged.txt
python code/drop_flagged.py flagged.txt
python code/shared_tokenizer.py --inputs data/pubmed_v2/clean_train.jsonl data/fineweb_v1/clean_train.jsonl --mb-each 400 --vocab-size 8192 --out tokenizers/mix8192.json
python code/prepare_data.py --src data/pubmed_raw  --out data/pubmed_v2 --skip-clean --tokenizer tokenizers/mix8192.json
python code/prepare_data.py --src data/fineweb_raw --out data/fineweb_v1 --skip-clean --tokenizer tokenizers/mix8192.json
```

## Reproducing the main results

Every number in the report comes from `results/results.csv`, and every row of that file is one
`runs/<name>/summary.json`. There are three levels of reproduction.

### Level 0 — regenerate all tables and figures (seconds, CPU only, no data)

```
python code/analyze.py results/results.csv --out report/figures
python code/analyze_similarity.py runs --pools results/pools_summary.json --scores data/similarity/scores.npz --out report/figures
```

The first command writes `fig1_main.png` … `fig6_horizon.png` and prints the noise estimate and the gain table.
The second writes `fig7_similarity.png` and `fig8_sim_distribution.png`. Both are deterministic given the committed
`results/`, `runs/` and `data/similarity/scores.npz` files, so this is the fastest way to check the report against
the repository.

The decile variants (`fig7_similarity_deciles.png`, `fig8_sim_distribution_deciles.png`) use
`--pools results/pools_summary_d.json` with `--name` and `--dist-name` set to the decile file names.

### Level 1 — re-run one cell (about 45 min on the GPU, needs the prepared data)

```
python code/train.py --domain-dir data/pubmed_v2 --general-dir data/fineweb_v1 --domain-frac 0.3 --domain-unique-tokens 10000000 --tokens 300000000 --lr 1e-3 --eval-interval 2000 --time-limit-min 45 --name check_U10M_d0.3
```

Expect test PubMed bits/byte **1.09 ± 0.01**; the three committed seeds gave 1.0875, 1.0929 and 1.0965.

### Level 2 — the full experiment grid

`python code/run_queue.py --lr 1e-3 --dry-run` prints every run with its settings (the saved plan is
`results/run_plan.txt`). Runs are resumable, so the queue can be stopped and restarted.

```
python code/run_queue.py --lr 1e-3 --max-priority 16     # core grid, baselines, dropout controls, seeds, horizon, U=1M/20M
python code/run_queue.py --summarize                     # -> runs/results.csv  (copy to results/results.csv)
```

This reproduces the 108 runs behind the report.

### Similarity extension

`data/similarity/scores.npz` is committed, so the similarity figures can be regenerated without a GPU (Level 0).
To rebuild the scores from scratch you need the checkpoints of `runs/S_Uall_d1.0_s1337` and
`runs/S_Uall_d0.0_s1337` (regenerated by Level 2), plus FineWeb shard 1 prepared like shard 0 into `data/fineweb_v2`:

```
python code/score_similarity.py --train-bins data/fineweb_v1/train.bin data/fineweb_v2/train.bin --pm-run runs/S_Uall_d1.0_s1337 --gen-run runs/S_Uall_d0.0_s1337 --ref-bins pubmed=data/pubmed_v2/val.bin fineweb=data/fineweb_v1/val.bin --tokenizer tokenizers/mix8192.json --out data/similarity/scores.npz
python code/build_pools.py --scores data/similarity/scores.npz --eval-bins data/pubmed_v2/val.bin data/pubmed_v2/test.bin --general-dir data/fineweb_v1 --out data/fw_pools --k 4 --tokenizer tokenizers/mix8192.json
python code/run_queue.py --lr 1e-3 --max-priority 19
```

Pause the queue while scoring: sharing the GPU slows training runs and can trip their 45-minute limit.

## The report

`report/` holds the submitted report and everything needed to build it:

| file | contents |
|---|---|
| `report/report.tex` | complete LaTeX source of the report |
| `report/references.bib` | bibliography (`\bibliography{references}`) |
| `report/figures/` | all figures, referenced via `\graphicspath{{figures/}}` |

`report/figures/` is committed and is exactly what Level 0 regenerates, so the figures in the report can be checked
against the repository without a GPU.

Figures are byte-identical only when regenerated with the same matplotlib version that produced them. The committed
figures were rendered with matplotlib 3.10.9, except `fig5_rule.png`, which was rendered with 3.11.2; its content is
identical but the PNG differs by 2 px in width. A different matplotlib version changes antialiasing and text metrics,
so compare figures visually rather than by hash.

To verify that the experiments described in the report can be reproduced from this repository:

1. Run the two Level 0 commands. They rewrite `report/figures/` from the committed `results/results.csv` and
   `runs/*/summary.json`, so any figure whose *content* changes indicates a mismatch between the report and the data.
2. Compare the printed gain table and noise estimate from `code/analyze.py` against the report's tables.
3. For any individual run, open `runs/<name>/summary.json` — it records the exact arguments, the model config, the
   library versions and the device, so each reported number can be traced to a single run.
4. To confirm the pipeline itself, run Level 1 and compare against the expected 1.09 ± 0.01 bits/byte.

## Notes on reproducibility

- Exact bit-for-bit reproduction is not expected: GPU non-determinism and a nightly PyTorch build both shift the
  last digits.
- Seed noise: pooled SD **0.0034 bits/byte** over 14 degrees of freedom (7 cells with 3 seeds each). A difference
  between two single runs therefore needs about **0.0095 bits/byte** ($2\sigma\sqrt{2}$) to be significant.
- Most cells are single-seed, so picking the best configuration per cell is optimistic by roughly 0.003–0.005
  bits/byte.
- All evaluation numbers are test bits/byte at the best-validation checkpoint (`best_test_domain_bpb`);
  `final_test_*` is the last weights.
- Not included in the repository: raw and prepared data, and checkpoints. Both are regenerated by the steps above.
  The exception is `data/similarity/scores.npz`, which is committed so the similarity figures stay reproducible
  without a GPU.
